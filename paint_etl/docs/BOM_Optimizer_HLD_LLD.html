BOM Optimizer — Production Persona

Requirements, high-level design and low-level design. Draft v0.1, 7 Nov 2026. Sources: BOM Optimizer RTM - V1.xlsx (all sheets + your two screenshots), the FDS v1.5, the SAP Data Reference workbook, and the existing code in src/bom/api and src/bom/ui.

0. "Ensure we have it" — do we?

Short answer: we have the shape of the product, but not the rules. The Excel gives the screen, the inputs, the ranking choices, the outputs and the data objects. It does not contain a rule list, formulas, or the SAP write-back method. Those are listed below as gaps so nobody assumes they exist.

In the Excel

  • One persona: Production (Planning and Sales sheets are empty or aspirational).
  • Inputs: Plant (mandatory), Material, Planned Order, Process Order, Production Line, then Rank 1 to Rank 4 (the screenshot shows Rank 1 = Cost).
  • Go button, then ranked cards: Material, Prod Version, Avg cycles, Avg reprocess cycles (e.g. "2 vs 6"), Cost (e.g. "40% reduction"), Proposed Recipe button, Legal approval status (yellow / green), Adopt button.
  • Ranking considers: history (time), cost, number of rework cycles, season, production line, production efficiency (hours, lead time).
  • Final quantity = original recipe + all goods issues (movement 261) on the process order.
  • Adopt must sync BOM / recipe changes to the process order in SAP.
  • Data objects: Material master, BOM, Routing / recipe, Production version; Planned orders; Process orders (header + components + operations); inventory; goods movements.
  • Load plan: one-time load for active materials, weekly batch for open planned orders and TECO'd process orders.

NOT in the Excel

  • A list of "industry rules". None exist as a rule list. Only criteria and a few remarks (active materials, raw-material grade, availability, legal).
  • How cost is calculated (which price field, price unit, currency).
  • What "rework / reprocess cycle" is, and how a rework order links to the original (the Questions sheet asks this; no answer).
  • Where legal approval status comes from (Planning item 3 and 4 are "open questions").
  • The SAP API and method for Adopt.
  • Column types, data volumes, user roles, authentication, performance targets.
  • The meaning of "78% / 96% / 100% Cycle 1/2/3" beside rank 1 (my reading: cumulative share of batches done by cycle 1, 2, 3 — to confirm).

So "are rules also in Excel only?" Mostly no. Ten requirement-level rules can be traced to the Excel (section 6), but each lacks parameters. The rest come from the old code or are my proposals and must be confirmed in a workshop with the client.

"4 tables" needs your confirmation. The Excel's Requirements sheet names four master-data objects (Material Master, BOM, Routing, Production Version) plus transactional objects (Planned Orders, Process Orders with header, components, operations). I read your "4 tables" as those four master objects, and I design them as the four core tables in Layer M (section 5). The transactional, refined and application tables sit around them because the persona cannot work without them. Earlier "4 tables" in the paint SQL document (STG_ORDER_*) are a different thing: the client's reporting steps, which become history inputs here.

1. Scope and persona

Product goal: a production planner enters a plant and (optionally) a material, planned order, process order and production line, orders up to four ranking criteria, and gets a ranked list of BOM / recipe alternatives, each with cost, rework evidence, season fit and legal status. The planner adopts one, and the system sends the change to SAP.

Roles (proposal — the Excel names none)

  • Planner: run analysis, view, request adopt.
  • Approver: approve adopt (needed because SAP write must be human-approved).
  • Rule admin: maintain rules, criteria, season map, legal status.
  • Viewer: read only.

Non-functional (all proposed)

  • Performance: analysis for one material under 5 seconds from pre-computed refined tables, not from raw SAP tables.
  • Determinism: same inputs and rule version always give the same ranking.
  • Security: SAP login through BTP (XSUAA); no SAP credentials in the app; role checks on every endpoint.
  • Audit: every analysis, rule change, approval and SAP call is recorded with user and time.
  • Volume: design for the 10 GB planned in the chat thread; the paint extract is about 1.7M rows.
  • Resilience: Adopt is idempotent; a failed SAP call can be retried without duplicate changes.

4. Data flow

4.1 Load flow (SAP → database)

  1. Select materials: multi-level BOM explosion from finished goods, take unique materials, keep only active (status, deletion flag), types FERT / HALB (and ROH / VERP for components). (Production → master logic 1–3)
  2. Master load (Layer M): Material (MARA, MARC, MAKT, cost from MBEW), BOM (header + items), recipe / routing (header, operations, components), production version (MKAL). Via the three OData services in FDS v1.5 (API_PRODUCT_SRV, API_BILL_OF_MATERIAL_SRV, API_MASTERRECIPE_0001).
  3. Transactional load (Layer T): one-time: process orders (header, components, operations) for active materials; weekly: open planned orders and TECO'd process orders; goods movements type 261 per process order; rework links.
  4. Refine (Layer R): after each load, rebuild candidates and statistics (4.2).
  5. Change pick-up: BOM changes daily or weekly by change date (FDS selection by variant).

Where the Excel files fit: the paint data (orders, rework movements, status, Cost Report) loads Layer T through the upload page we already built, so work can start before BTP access exists.

4.2 Refine flow (building candidates)

For each material + plant:
  1 STANDARD    : the BOM + recipe of each production version (MKAL) valid today
  2 ALTERNATE   : other BOM alternatives / versions of the same material
  3 HISTORICAL  : for each past process order, final quantities =
                    original recipe quantities + all goods issues (261) on that order,
                    grouped by identical component set
  Normalise each into one candidate (components + quantities per base unit).
  Per candidate store stats: times used, last used, average reprocess cycles,
                    cost per unit, operation hours, season counts, lines used.

4.3 Run flow (user clicks Go)

  1. UI posts selection + ordered criteria to POST /api/production/analyze.
  2. API resolves the anchor (material / order), reads the current BOM as baseline.
  3. Loads candidates for the material and plant; applies hard rules (infeasible ones are flagged with a reason, not silently dropped).
  4. Computes criterion values, ranks lexicographically by the user's order, builds the "why" text.
  5. Stores the run in Layer A (inputs, rule version, every candidate and its score) and returns the cards.

6. Rules engine

6.1 Design

  • Rules are rows in a_rule. Each points to a registered Python handler function plus JSON params; no free-form code is stored in the database.
  • Types: HARD (candidate infeasible, with reason), WARN (shown, still rankable), FILTER (removed before ranking), FLAG (adds a badge, e.g. legal yellow).
  • Rules run in exec_order. The set used is versioned in a_rule_set and stored on every run.
  • Ranking criteria are separate (a_criterion): the user chooses and orders them per run; the rules decide who may compete.
  • Admin screen: list, enable / disable, edit params, reorder, with every change in a_audit_log.
handler signature:  def rule_x(candidate, context, params) -> RuleResult(passed: bool, message: str)
engine:  for rule in active_rules_in_order: result = HANDLERS[rule.handler](c, ctx, rule.params)
         HARD fail -> feasible=False + violation text ; WARN -> warning ; FLAG -> badge

7. Ranking and metrics

7.1 How ranking works

  1. Hard rules split candidates into feasible and infeasible (infeasible are listed last with reasons).
  2. Within feasible, sort by Rank 1, then Rank 2, then Rank 3, then Rank 4 (lexicographic, the existing rank_by_criteria). Last tie-breaks: more historical uses, then candidate id, so results are stable.
  3. Each criterion has a direction (cost lower is better, recency newer is better).
  4. A plain-English "why" is generated from the values (existing build_rank_reason).

7.3 A weakness to fix before building

With strict lexicographic ranking and decimal values such as cost, two candidates almost never tie on Rank 1, so Rank 2 to 4 would almost never matter, and the user's extra choices would look ignored. Fix: each criterion has a tie band (a_criterion.tie_band_pct). Values within the band count as equal, so the next rank decides. Example: cost within 2% = tie. The old engine does not do this yet.

Behaviour

  • Plant is mandatory; Go disabled until set. Giving a process or planned order fills material and line automatically.
  • Rank dropdowns offer only criteria from /api/criteria; a criterion can be used once.
  • Legal chip: green approved, yellow pending, red restricted. Adopt is disabled unless green (rule R-10).
  • Proposed Recipe opens a side-by-side panel: current vs proposed components, quantities, operations, differences highlighted.

  • Admin screens (rules, criteria, season map, legal status) are separate pages for the rule admin role.
  • Empty and error states: no candidates, no history (show "no evidence" instead of 0 cycles), SAP unreachable.

10. Adopt and the SAP connection

Path

FastAPI worker → BTP Destination (points at S/4 with the user's identity or a technical user) → Connectivity service → Cloud Connector → S/4HANA OData. The Cloud Connector link in the chat thread is for the tunnel only.

Write steps

  1. Pre-check, read live from SAP: order exists, status still allows change (not confirmed, not TECO), version/ETag unchanged since analysis.
  2. Build the change: replace component list and quantities (and operations if the recipe differs).
  3. Send with an idempotency key; keep request and response in a_adoption.
  4. On success set CONFIRMED; on SAP error keep FAILED with the message; retry only reuses the same key.
  5. Re-read the order and store the SAP-side result as proof.

Candidate SAP APIs

Not verified. Likely standard options are the Process Order OData service (for components and operations of a process order) and the Bill of Material service (which allows changes to a BOM). Which one, and whether a released order can be changed this way, must be confirmed by the SAP team; the Excel says only "sync". Changing the master BOM is a bigger action than changing one order and should not be done by Adopt without explicit agreement.

Safety

  • No write without approval and a green legal status.
  • A feature switch SAP_WRITE_ENABLED off by default; today's code already only stages.
  • Full audit: who requested, who approved, what was sent, what came back.
